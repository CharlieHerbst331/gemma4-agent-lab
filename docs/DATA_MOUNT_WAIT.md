# Competition mount wait

The smoke4 kernel (single-v3 vs single-v4) failed twice in generated-notebook cell 3 with `FileNotFoundError` for `/kaggle/input/competitions/gemma-4-developer-agent/tasks.jsonl`. A CPU probe with the same competition, wheelhouse v30, and model sources found that path present, including `tasks.jsonl`. Earlier GPU runs worked. The likely cause is a late or empty competition mount on some workers, not a new layout.

Cell 3 is our payload cell (`_pair_payload_cell` in `src/gemma_lab/notebook.py`), not leftover official-starter text. It still uses that same path and `load_tasks`. Before the read it polls `DATA_DIR / 'tasks.jsonl'` every `DATA_WAIT_INTERVAL_SECONDS` (5) for up to `DATA_WAIT_TIMEOUT_SECONDS` (300). A file is ready only when it is non-empty, ends with a trailing newline, and every line parses as JSON. A blank line is not a record: a file that is only a newline, or only blank lines, is `empty` and stays not ready. A half-written file with no trailing newline is `truncated` and keeps retrying. A line that is not JSON, including a blank line mixed with JSON lines, is `unparseable` and also retries. Any exception while checking counts as not ready (`unreadable`, or `missing` if the path is gone). The first miss is logged, then about every `DATA_WAIT_LOG_EVERY_SECONDS` (30), and one line is printed when the file is ready. A file that is already there returns without sleeping. `data_wait_seconds` is that wait rounded to one decimal, so an already-present file records `0.0` rather than a tiny scientific value.

On timeout the cell runs `ls -la /kaggle/input /kaggle/input/competitions` and `find /kaggle/input -maxdepth 4 -name tasks.jsonl`, each with a subprocess timeout, and writes that text to `/kaggle/working/data_mount_probe.txt` before raising `FileNotFoundError`. The error names the last check: `missing`, `empty`, `truncated`, `unparseable`, or `unreadable`. The wait is merged into `/kaggle/working/run_manifest.json` as `data_wait_seconds` and copied onto the in-kernel pair manifest.

`path.stat()` and the following read have no timeout. A failing stat or read is treated as not ready, but a hung mount call is not bounded: Python has no portable timeout around `stat` or `read`, and this check does not add a thread or signal around it.

The wheelhouse cell (notebook cell 1, official starter plus the empty-wheelhouse fallback) globs `WHEELHOUSE_DIR` immediately. The server cell (notebook cell 5) passes `MODEL_PATH` (`/kaggle/input/models/google/gemma-4/other/gemma-4-31b-it-qat-w4a16-ct/2`) straight into model setup. Those are directory mounts, not this file check, so they do not use this wait. A real Kaggle mount delay was not reproduced here.

`gemma-lab pair-report` also checks `protocol_sha256` on a stored `pair_manifest.json` against the protocol file hash (`load_protocol` `_sha256`). Three smoke protocols share schedule hash `31398c6c…`, so a schedule match is not enough: an old smoke2 manifest fed to the think256 protocol used to print a report under the wrong protocol. A differing hash is a `ValueError` that names both hashes. This checkout has no stored real `pair_manifest.json`. The report fixtures in tests omit `protocol_sha256`. A manifest that lacks the field, or has it blank, still reports, with a warning that older runs are accepted without that check.
